# pi local deployment

Runs `@earendil-works/pi-coding-agent` (the "pi" agent harness) in a
long-lived container named `pi-sandbox` as the backend for gmail-search's
deep-analysis mode. The Python driver (`runtime_pi.py`) runs one
`docker exec -i … pi --mode rpc …` per turn against this container;
`pi` itself never runs on the host. The extension at
`extensions/gmail-tools/` bridges pi's tool-call protocol to the host
MCP tools server at `http://host.docker.internal:7878/mcp`.

## Layout

- `Dockerfile` — builds `gmail-search-pi:local` from `node:24-bookworm-slim`,
  installs `pi`, and bakes in the `gmail-tools` extension (with its own
  `node_modules`, `npm ci --omit=dev`).
- `docker-compose.yml` — service definition for `pi-sandbox`.
- `extensions/gmail-tools/` — the pi extension source (Task 8). Copied
  into the image at `/opt/gmail-tools`; its `node_modules/` is
  gitignored and rebuilt at image build time.
- `sessions/` — mounted at `/sessions` inside the container. Per-conversation
  `--session <path>.jsonl` transcripts live here so a conversation can
  resume across turns. Gitignored.
- `pi-agent/` — mounted at `/home/pi/.pi/agent`. Holds `auth.json` after
  `/login` and other per-install pi state. Gitignored.
- `../claudebox/workspaces` — mounted at `/workspaces`, shared with the
  claudebox deploy. Each turn runs with `-w /workspaces/<workspace>`; the
  driver creates the subdirectory before exec'ing.
- `.env` — holds `GMS_MCP_URL`, `GMAIL_MCP_SERVICE_TOKEN`, and one of
  `ANTHROPIC_API_KEY` / `GEMINI_API_KEY`. Auto-generated by `setup.sh`,
  gitignored, mode 600.

## Start / stop

```bash
bash deploy/pi/start.sh   # runs setup.sh, brings up compose, waits for `pi --version`
bash deploy/pi/stop.sh    # docker compose down
```

`start.sh` builds the image, brings the container up, and confirms
`docker exec pi-sandbox pi --version` answers before printing `Ready.`.
On failure it prints the last 40 lines of container logs and exits
non-zero.

## Logging in

pi needs a provider credential. Either:

- Put a key in `deploy/pi/.env` before starting — `GEMINI_API_KEY=…`
  (gmail-search's deep-mode default provider is Gemini) or
  `ANTHROPIC_API_KEY=…`; or
- Run `docker exec -it pi-sandbox pi` and use `/login` interactively.
  Tokens land in `pi-agent/auth.json` on the host (mounted at
  `/home/pi/.pi/agent`), so they survive container restarts and rebuilds.

## The service token

The host MCP server can enforce transport-token auth on `/mcp`
(`GMAIL_MCP_REQUIRE_TRANSPORT_AUTH=1`). When that is on, an
unauthenticated `/mcp` client gets a 401. `pi-sandbox` is a **trusted**
container that the server-side orchestrator drives directly — the
orchestrator registers a per-turn session (`register_session(session_id,
user_id=...)`) via the admin API before each turn, and per-tenant
scoping comes from that **registered session**, not from any static
config baked into the container.

So `pi-sandbox` must NOT use a tenant-bound transport token (that would
pin every turn to a single owner — a cross-tenant bug). Instead it uses
a tenantless **service token** (`aud=mcp-service`): it satisfies
enforcement but carries no identity, so scoping stays on the registered
session.

`setup.sh` mints a fresh service token automatically the first time it
runs, if `.env` doesn't already have one: it reads
`GMAIL_MCP_ADMIN_TOKEN` from `~/.config/gmail-search/mcp.env` and calls
`POST /admin/service-tokens` (host-local only). It does **not** copy
another deploy's token — a stale/expired token elsewhere (e.g.
claudebox's `.env`) should never leak into this deploy.

`docker-compose.yml` passes the token into the container as
`GMAIL_MCP_SERVICE_TOKEN`; the `gmail-tools` extension reads it from its
own process environment and sends it as `Authorization: Bearer <token>`
on the MCP connection. It is never placed on a command line — `pi
--mode rpc` argv carries only `GMS_SESSION_ID` and the extension path;
the secret is read from the container's own env by the extension.

Service tokens are long-lived static credentials; rotate by deleting the
`GMAIL_MCP_SERVICE_TOKEN=` line from `.env` and re-running `start.sh`
(or `setup.sh`), which mints a fresh one. `/admin/*` endpoints are
loopback-only by default, so minting only works run from the host.

## Security posture

`pi-sandbox` is **one shared sandbox** for every deep-mode turn from
every user, running as a single UID with a single provider key and a
single tenantless MCP service token — the same model as the
`claudebox` deploy. Every turn's `bash` tool can see every other
active or recent turn's workspace, session transcripts, and process
environment (including `GEMINI_API_KEY` / `ANTHROPIC_API_KEY` and the
service token); tenant scoping comes entirely from the
per-turn-registered MCP session, not from container-level isolation.
Treat this as a **single-tenant or trusted-multi-user** deployment
until per-session isolation (separate container/namespace/UID per
turn, or a token broker that keeps the service token out of the
agent's own shell environment) exists. For anything closer to
multi-tenant, set `GMAIL_PI_BUILTIN_TOOLS=0` — this disables pi's
`bash` tool (no shell in the sandbox), which removes the main path a
turn could use to read another turn's environment or files.

## Smoke test

Without a registered session the extension is deliberately not loaded —
this checks the bare harness answers over the RPC protocol:

```bash
docker exec -i -e GMS_SESSION_ID=smoke pi-sandbox pi --mode rpc --no-extensions --no-skills \
  --no-context-files --no-session --no-tools <<'EOF' | jq -c 'select(.type=="message_end")'
{"type":"prompt","message":"Say only the word OK."}
EOF
```

To exercise the real driver path end to end (extension loaded, MCP
tools reachable, a real session registered), see Task 9's smoke script
in `.superpowers/sdd/2026-09-02-pi-deep-backend/task-9-report.md` — it
registers a throwaway session via the admin API, drives one turn through
`runtime_pi.drive_turn`, and unregisters the session afterward.
