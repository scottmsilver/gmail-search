# TEXT partition release: caller inventory

## The uncommitted tree targets the abandoned numeric profile — read this first

2026-09-16. Before writing any caller change, know that the worktree currently
contains work aimed at the **numeric** profile, which the mixed-owner plan later
rejected in favour of TEXT ("this still avoids adding `search_id`").

| | Live / main | Uncommitted worktree |
| --- | --- | --- |
| `messages.search_id` | absent | `BIGINT GENERATED BY DEFAULT AS IDENTITY UNIQUE` added |
| BM25 index | `bm25(id, subject, body_text, from_addr, to_addr) key_field=id` | conditional `key_field='search_id'` index |
| `queries.py` BM25 score | `paradedb.score(id)` | changed to `paradedb.score(search_id)` |

Verified against the live database: `public.messages` has `id`/`user_id` and no
`search_id`, and the installed index is `key_field=id`. Live therefore already
matches the TEXT shape — which is exactly why TEXT was chosen.

**Deploying the worktree as-is would add a column, build a second BM25 index and
re-key scoring on the live database.** Worse, the BM25 callers wrapped every
failure in `except Exception` and returned `{}`, so a mismatch would not surface
as an error — search would simply stop ranking. That is the same shape as the
nine-day silent search outage in the project's history.

### Done 2026-09-16

`store/queries.py` realigned to the TEXT key and made honest:

- `_pg_bm25_messages` and `_pg_bm25_attachments` were near-identical; both now
  call one `_pg_bm25_scores` helper, so the query shape exists once.
- The key lives in a single constant, `_BM25_SCORE_KEY = "id"`, instead of four
  drifting string literals. A profile change is now one edit.
- A schema/profile mismatch (SQLSTATE `42703`, `42P01`, `42883`, `3F000`)
  **propagates**. Transient faults keep degrading quietly, as before.

Covered by `tests/test_store_bm25_profile.py` (6 tests), including one that
fails if a mismatch is ever silently downgraded to an empty result again.

### Connection-level profile binding — done 2026-09-16

`store/schema_profile.py` is the single answer to "what shape is this database?"

- **Selected, not inferred.** `selected_profile()` reads `GMS_SCHEMA_PROFILE`
  and defaults to `text-key-v1`, which is the live shape. Sniffing the catalog
  is what lets two call sites reach different answers, so nothing does it.
- **Carried on the connection.** `_connect_pg` binds `conn.profile`, so all ~60
  call sites inherit the selection without changing their signatures.
- **Verified once, then cached per DSN per process.** A database that disagrees
  raises `SchemaProfileMismatch` at connect — before any mailbox work — naming
  both the expected and the observed shape. There is no fallback and no retry.
  `GMS_SKIP_SCHEMA_PROFILE_CHECK=1` exists for bootstrap paths.
- **Consumed, not decorative.** `queries.py` and `propositions.py` now take the
  BM25 key from `schema_profile.bm25_key(conn)` instead of literals.

Covered by `tests/test_schema_profile_binding.py` (8 tests), including one that
fails if a mismatched database is ever accepted at connect.

**The binding paid for itself on its first run**, refusing the test database:

```
selected profile 'text-key-v1' expects key_field='id' partitioned=False,
but the database has key_field='search_id' partitioned=False
```

That was `pg_schema.sql` still building the numeric shape.

> **Correction, 2026-09-16.** This document previously claimed that was "Fixed:
> the `search_id` identity column is gone." It was not. Removing the column
> broke 41 gateway tests, which build their fixtures from `pg_schema.sql` and
> then run the numeric migration, so the change was fully reverted and the
> conftest declared the numeric profile instead. The divergence was still there;
> only the claim had moved. It is closed now, by the fences below.

### The TEXT installer — done 2026-09-16

`pg_schema.sql` installs whichever shape the process selected, rather than one
shape for everybody:

```sql
-- >>> profile-only: numeric-key-v1
    search_id BIGINT GENERATED BY DEFAULT AS IDENTITY UNIQUE,
-- <<< profile-only: numeric-key-v1
```

`db._read_pg_schema()` keeps a fenced block only for the profiles that name it,
and is now the single reader — `_init_db_pg` applies its output instead of
reading the file a second time, so the text that gets installed is the same text
the table-docs assertion is checked against. The BM25 index block needed no
change: it already selected its key from whether the column exists.

One file and one applier, not a second schema to keep in step. A separate
`pg_schema_text.sql` would have had to be diffed against this one forever.

Nothing migrates an existing database. A database whose shape disagrees with the
selection is refused at connect, as before.

Covered by `tests/test_fresh_install_matches_profile.py` (10 tests), which
installs each shape into its own schema and then asks the *connection binding*
to verify it — installer and binding have to agree, which is precisely what they
did not do before.

That test found a second defect while being written: `observed_shape()` returned
`key="id"` whenever it could not find a BM25 index, so an **empty database
satisfied the TEXT profile**. A database with no `messages` table at all would
have passed verification and then failed on the first query. It now reports
`None` and `verify()` raises, naming the bootstrap escape hatch.

### SQL examples rendered from the profile — done 2026-09-16

`db.py:TABLE_DOCS`, `server.py` (both the LIKE-rejection message and the
schema-endpoint preamble), `agents/analyst.py` and `agents/mcp_tools_server.py`
took the message key from `schema_profile.selected_bm25_key()` instead of a
literal. These are documentation strings, which is exactly why they rotted:
nothing failed when they said `search_id` against a database keyed on `id`. What
fails is downstream — the model copies the example back as SQL and gets
`column "search_id" does not exist`.

`TABLE_DOCS` entries are now templates carrying `{bm25_key}`; read them through
`table_docs()`. Attachments and propositions keep `id` in every profile and were
deliberately left alone — only the message key moves.

Covered by `tests/test_bm25_examples_follow_profile.py` (12 tests): a
behavioural check per renderer per profile, plus a source-level check that
catches the next example added by copy-paste.

### Security audit, 2026-09-16

CLAUDE.md's two-track audit ran. Track 2 could not use codex (out of credits
until Sep 22), so an independent-context reviewer took the same brief. Every
finding below was re-checked against the engine or the catalog before acting —
two of them turned out to be the reviewer's mistake, and one of *those* still
exposed a wrong comment of mine.

**Fixed:**

- **The production apply token could not tell production from a copy of it.**
  `system_identifier` is issued at `initdb` and copied verbatim by every
  physical copy. Measured here: live and `data/pg-backup-16.13-20260916` both
  report `7630921061527392295`. Since the runbook has the operator take that
  backup immediately before the window, holding both at once is the *normal*
  state. Closed with a marker nonce written into the target
  (`COMMENT ON DATABASE … IS 'gms-migration-target:<32+ hex>'`), now the third
  field of the token; a copy taken beforehand cannot carry it.
- **The backup check was a file-existence ritual.** It now reads
  `global/pg_control` offset 0 — a little-endian uint64, verified against this
  project's own backup — and refuses a backup of a different cluster by name,
  plus a 48h recency bound. For anything that is not a data directory it falls
  back to "exists, non-empty, recent" and says so rather than claiming more.
- **Fence-parse failure was fail-open.** A missing closing marker, a mismatched
  profile list, or a CRLF checkout made the regex miss, leaving the fenced DDL
  installed for *every* profile. Now raises. All three cases verified.
- **`key_field` was read by substring search** over the joined reloptions text.
  Now reads the `text[]` element.
- **The MCP tool description resolved the key at import**, so a process
  configuring the profile later would disagree with `server.py`, and an invalid
  profile became an import-time traceback. Now resolved per call.
- **Forwarded owner ids were unvalidated.** Pre-existing and gated behind
  `GMAIL_MCP_ADMIN_TOKEN`, but `require_user_id` returned `X-User-Id` verbatim
  and it reaches `server.py`'s schema preamble, which splices the owner into
  `WHERE user_id = '…'` examples the model is told to copy. A quote there breaks
  the scoping the preamble exists to enforce. Constrained at the boundary.

**Raised, checked, not defects:**

- *"A partitioned install may attach the BM25 index to children, so
  `observed_shape` returns `None` and every connection is refused after the
  migration."* Measured against a real partitioned database: `CREATE INDEX` on a
  LIST-partitioned parent makes a partitioned index (`relkind='I'`) whose
  `indrelid` is the parent, so the probe finds it and `verify()` accepts
  `text-partitioned-v1`. Pinned by a test, since it is a property of
  PostgreSQL's catalog rather than of our code and it guards the migration
  target.
- *"An index created with no `WITH` options keys on `id`, so treating NULL
  reloptions as 'no index' is wrong."* pg_search 0.23.0 **refuses** such an
  index outright: `index should have a WITH (key_field='...') option`. The
  conflation is sound — but my code comment had asserted the opposite and would
  have misled the next editor. Comment corrected to the measured behaviour.

**Accepted, with reasons:**

- `_local_connection` proves only that a DSN does not plainly name a remote
  host. An `ssh -L`, socat or pgbouncer on loopback defeats it, and a forwarded
  socket is indistinguishable from a real one. Kept as a cheap first filter; the
  docstring and the phase-one doc now say so instead of claiming remote targets
  are "refused outright". IPv6 loopback spellings are *rejected* rather than
  accepted — a gap on the safe side, flagged in the code so nobody closes it by
  loosening the check.

**Deliberately not fixed, recorded here instead:**

- `gateway/partitions.py:297` still defaults `profile=NUMERIC`. The explicit
  requirement landed only at the admission boundary, so a new non-admission
  caller re-opens the defect. Making it required is ~53 mechanical call-site
  edits, nearly all in tests that want NUMERIC; worth doing, not worth bundling
  into this change.
- **Two shape selectors that are never cross-checked.**
  `PartitionSchemaProfile` (admission) and `SchemaProfile` / `GMS_SCHEMA_PROFILE`
  (readers) are independent, and nothing asserts they agree. Provisioning
  partitions in one shape while every reader is bound to the other is exactly
  the class of split this work set out to close, and it is still open at the
  seam between the two.

**Track 1 (dependencies):** 123 known vulnerabilities across 11 packages, all
pre-existing and all recorded as deferred on 2026-09-03. Two now sit on the
invited-launch path and should be bumped before invitees reach the app: **pyjwt**
2.12.1 → 2.13.0 (handoff-JWT verification) and **starlette** 1.0.0 → 1.3.1 (the
public listener). Note `uvx pip-audit` with no arguments reports "No known
vulnerabilities found" — it audits uvx's own environment, exits 0, and reads as a
clean audit. Use `uv run --with pip-audit pip-audit`.

## Qualified internal path

`gateway/partition_profiles.py` defines explicit numeric and TEXT partition
profiles. Credentials, role names, fixed columns, native index definitions and
catalog audits bind the selected profile. The TEXT message key is `id`; there is
no message identity sequence or `search_id` column. Attachment/fact numeric keys
remain qualified by owner. Runtime profile mismatch fails before database
admission; actual catalog drift fails before index acquisition/provider work.

The full public runtime should use these fixed gateway operations. Its guest
cannot choose a schema profile, owner, database connection or search model.

## Legacy callers needing a compatible release

| Location | Current dependency | Required change |
| --- | --- | --- |
| `store/db.py:get_connection`, `_connect_pg`, `_PgConnWrapper` | About 60 callers share the compatibility wrapper; no schema-profile binding | Add a trusted startup selection and carry it on the connection. Verify selected shape before mailbox work; preserve transaction ownership. Do not infer selection from columns or retry another shape after SQL failure. |
| `store/queries.py:_pg_bm25_messages` | Two hardcoded `score(search_id)` branches; table-wide `messages @@@`; catches errors and returns partial/empty scores | Use the selected key and qualified parent with an immutable, safely quoted owner restriction. Profile mismatch must propagate; never become a valid empty result. Test restricted/unrestricted generic and custom plans. |
| `store/queries.py:_pg_bm25_attachments` | Table-wide match and parameterized optional owner | Require the trusted owner for the partitioned profile and use the qualified fixed owner-literal shape. Keep message-candidate predicates bound. |
| `propositions.py:backfill` | Hardcoded `search_id @@@`; owner parameter | Select the trusted message key and fixed owner restriction before any extraction/provider work. |
| `search/engine.py` | Calls the above FTS functions | Propagate the qualified connection/profile; retain existing score and filter behavior. |
| `store/db.py:TABLE_DOCS` | Numeric-key examples | Render examples from the same trusted profile used by the service. |
| `server.py` | Slow-query suggestions and schema endpoint examples use `search_id` | Generate matching examples. Never interpolate an owner into executable SQL without psycopg quoting. |
| `agents/analyst.py`, `agents/mcp_tools_server.py` | Static numeric-key performance hints | Generate profile-correct documentation; runtime guest SQL remains governed by its existing restricted compiler. |
| `store/pg_schema.sql` and `init_db` | Numeric identity default plus conditional column-existence BM25 installer | Separate a fresh qualified TEXT installer from the historical schema. Explicitly reject a mismatched existing database; no migration or automatic index rebuild at application startup. |
| Admission and ingestion composition | Partition provisioning defaults numeric | Pass the trusted TEXT profile consistently through partition readiness and search credential installation. Qualify owner-scoped CRUD against the migrated schema before enabling writers. |

The compatibility wrapper currently accepts only `db_path` (ignored in favor of
the trusted DSN configuration), and callers use both mapping and positional rows.
A profile implementation must preserve those interfaces or update every caller
explicitly. Test DSNs use isolated schemas; tests for the new qualified profile
must instead use complete disposable databases with its canonical public/private
schema contract. Do not weaken the production catalog checks to accommodate old
test fixtures.

## Remaining qualification

1. Complete and independently review the synthetic direct legacy TEXT migration.
2. Implement trusted caller/schema selection with mismatch tests before any
   extraction, inference, embedding or native index loading.
3. Verify both-owner search, ingestion, summary, proposition, attachment and
   deletion paths against the actual migrated schema, including colliding IDs.
4. Measure B-tree construction, foreign-key validation, lock time, peak space
   and WAL on representative data; rehearse rollback and backup restore.
5. Release the matching application and writer profile together with the
   migration. Existing worker image pins and live services remain unchanged
   until their separate full-runtime and sign-in gates pass.

No full database copy is proposed. The revised mixed-owner strategy preserves
dominant mailbox heaps/TOAST, moves minority rows and rebuilds retained BM25
indexes in a fresh transaction after redistribution commits. Owner-qualified
B-trees, foreign-key validation, copying and rebuilding require measurement.
Durable maintenance/readiness gating is required throughout the staged process;
catalog shape alone cannot establish clean historical search statistics.
