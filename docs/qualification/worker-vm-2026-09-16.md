# Worker VM on the mail host: built and validated

2026-09-16. A dedicated execution worker now exists as a KVM guest on `sukkot`
rather than on separate hardware. This records what was built, what was proved,
and what still has to be closed before enrolment.

## Why a guest here, and what it costs

The design requires a dedicated Linux VM and forbids running on the mail host.
A KVM guest satisfies the first — own kernel, own disk, no shared filesystems —
while sharing physical hardware with the mail database. That is a deliberate
trade: it defends fully against a prompt-injected agent doing something stupid,
and imperfectly against a hypervisor escape. Separate hardware remains strictly
better and this should move if a spare box appears.

## Built

| Property | Value |
| --- | --- |
| Domain | `gmail-execution-worker` (libvirt, `qemu:///system`) |
| Guest | Debian 13 genericcloud, **UEFI boot** |
| CPU / RAM / disk | 4 vCPU `host-passthrough`, 8 GiB, 40 GiB |
| Network | libvirt `default` NAT, `192.168.122.64` |
| Access | `~/.ssh/gmail_worker_ed25519` → `debian@` |
| machine-id | `9265ee8e693842b1b1461c41586f96a3` |

**UEFI is required.** The first build used BIOS and the guest sat in a reboot
loop — GRUB started, the kernel died within about two seconds, repeatedly. The
symptom from outside is only "no DHCP lease" and a pegged vCPU, so check the
console before assuming a network fault. `virsh console` needs a controlling
TTY; `script -qec "virsh console <dom>" /dev/null` gives it one, and the serial
log file libvirt writes is root-owned and not readable from the user account.

## Proved, not assumed

- **Nested virtualisation works.** `KVM_CREATE_VM` succeeds inside the guest
  (KVM API version 12), which is the README's explicit prerequisite. Host has
  `kvm_intel.nested = Y`; the guest sees `vmx` and has `/dev/kvm`.
- **cgroup v2** present (`cgroup2fs`).
- **The guest cannot reach the mail database.** From inside, the host gateway
  `192.168.122.1` was probed:

| Port | Service | Result |
| ---: | --- | --- |
| 5544 | mail PostgreSQL | **blocked** — binds `127.0.0.1` |
| 8090 | `serve` | **blocked** — binds `127.0.0.1` |
| 7878 | MCP tools server | **reachable** — binds `0.0.0.0` |

## Two things to close before enrolment

**1. The MCP tools server is reachable from the LAN.** It binds `0.0.0.0:7878`
while its cloudflared tunnel connects to `http://localhost:7878`, so the wide
bind buys nothing. It does demand OAuth — an unauthenticated request gets 401 —
so this is excess exposure rather than an open door, but the worker VM and
anything else on the network can reach it. Binding `127.0.0.1` would keep the
tunnel working and remove the exposure. Not changed here: it is a live service
and the change deserves its own restart.

**2. The guest still has general outbound network.** The README requires none —
the worker needs only the controller's inbound SSH. Restrict before enrolment,
not after.

## Not yet done

Enrolment itself: the unprivileged `gmail-full-agent-rpc` and
`gmail-gateway-tunnel` accounts, sshd forced-command policy, the five pinned
assets (`firecracker`, `jailer`, `vmlinux`, `rootfs.squashfs`,
`agent-full.squashfs`), and `production.json` carrying the machine ID above.
The qualified guest image is recorded as SHA-256
`968d41e5875b18044282901c6848f1a257833f2f875ec4ac2cddf83bf29da703` and currently
exists only in a disposable scratch directory — it needs a verified export.

## Teardown

```sh
virsh --connect qemu:///system destroy gmail-execution-worker
virsh --connect qemu:///system undefine gmail-execution-worker --nvram
virsh --connect qemu:///system vol-delete --pool default gmail-execution-worker.qcow2
```
